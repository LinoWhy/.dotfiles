# 文稿写作与修订

## 确定文稿要解决的问题

从请求和已有材料判断读者已有的知识、读完后要完成的事，以及文稿承担的职责。信息足够时直接开始；只有影响内容选择且无法推断的缺口才需要询问。这些判断用于写作，不必逐项写进成稿。

按用途选择主线：操作说明沿行动顺序展开，机制解释沿对象关系或因果展开，比较与建议围绕判断维度展开。沿用用户指定的体裁和格式，不强制统一章节。

## 组织初稿

- 逐段判断它回答哪个读者问题。准确但不服务本文用途的信息可以删除、移到合适位置或链接已有说明；必要背景在使用时引入。
- 将执行前必须知道的条件放在对应操作之前；将改变结论含义的范围、假设和不确定性放在结论附近。区分事实、推断和建议，不用泛化免责声明替代具体条件。
- 用连续段落解释关系，用列表承载并列项或步骤，用表格比较共同维度。不同形式各有作用，不逐项复述同一内容。
- 检查长句中的动作、对象和条件是否清楚，拆分后补足必要连接。陌生术语随相关对象解释，不为变化措辞而更换名称；中文不套用英语词数、时态或受控词典限制。

## 修订已有文本

先判断问题属于信息取舍、组织顺序还是句子表达，再改对应部分。保留原意、必要限定和已有正确内容，不把局部修改扩大为全文重写。

将补充和纠正融入原有论述，删除被替代的表述，不把讨论经过追加成正文。维护规范时，在承担该职责的位置修改原条款；已有规则用引用连接，避免复制出多个维护位置。

需要校准内容取舍或改写幅度时，参照[改写示例](references/examples.md)。

## 成稿检查

按目标读者的已有知识，只看成稿，检查：

- 能否回答核心问题，或完成预期操作、判断？
- 是否缺少必要前提、概念或关系，是否把尚未确定的事写成定论？
- 哪些段落删除后不损失理解或行动所需的信息？

修正发现的问题后交付成稿。除非用户要求审阅意见，否则不附这份检查过程。重要长文可用脱离聊天背景的阅读检查进一步验证；简短文本无需额外流程。
